# report-gepa:计划

用 GEPA 优化写报告页面的提示词。旧目录(`ui-judge`、`ui-loop`、`ui-rl`、`data-collection`)原样保留,这里不引用、不复制其中的代码、数据、标注和结论,全部从头做。

## 动机

DeepSeek 写网站首页写得好,把 JSON 数据交给它写报告页面却写得差。我们的判断是模型有能力,但提示词没有调出这种能力,所以做提示词优化。

## 已定的选择

| 项 | 选择 |
|---|---|
| 优化方法 | GEPA(arXiv 2507.19457),用官方库 `gepa==0.1.4` |
| 语言 | Python 3.13,虚拟环境在 `.venv/`(不进 git) |
| rubric | 从这里新做的人工标注理由里归纳,只写有依据的条目 |
| judge 校准 | 照 MiMo-V2.6 技术报告 4.2.2、4.2.3 节和它开源的 `recipes/design` 打分服务的做法(见第 5 节) |
| 密钥 | 只放在 `~/.config/report-gepa/llm.env`,不进仓库 |
| 端点 | `https://openoneapi.com/v1`,OpenAI SDK |
| 生成页面 | `deepseek-v4.1-flash`(被优化的对象) |
| 主 judge | `glm-5.3-flash`:和生成模型不同家,避开 judge 偏爱自家输出 |
| 交叉重判 | `deepseek-v4.1-flash`:5.2 节第 1 步换模型重判用 |
| 反思改写 | `deepseek-v4.1-flash` |

两个模型 2026-10-19 都试过读截图里的数字,都读对。

## 1. 数据

新写一批报告数据(JSON),是生成模型的输入。规格待定(见第 8 节)。划分为训练、验证、测试三份:

- 训练:GEPA 的 D_feedback,每轮从中抽 3 份产生改进意见。
- 验证:GEPA 的 D_pareto,给每个提示词版本打分、做帕累托挑选。
- 测试:只在最后用一次。测试集用训练和验证里没出现过的报告结构,检查学到的东西能不能换到新结构上。

另有一组真实数据:The Pudding 公开的 20 个数据集(`the-pudding/data`,MIT 许可),每个都有已发表的文章。Pudding 是我们的标杆:原文截图给标注当参照、给细则归纳当高分样例。哪些进 GEPA 的哪一份,等标注后再定。

数据放 Google Drive,`README.md` 写清楚取回方法。

## 2. 生成和渲染

- 生成:pi agent 写页面。系统提示词是被优化的指南;用户消息是固定的任务说明,只说数据在 `data/`、页面写到 `index.html`,不放数据本身。agent 用读文件和沙盒里的 shell(python3、node,没有网络、没有密钥)自己读数据、算数,再写页面。这样几十 MB 的 CSV 也能用。
- 渲染(`src/report_gepa/render.py`):Chromium 整页截图,沿用 MiMo 渲染服务里每条都对应过真实事故的处理:
  - 用本地 http 服务打开页面,不用 `file://`(`file://` 下模块脚本和 fetch 会被拦,页面白屏);
  - 截图前先滚到底,让懒加载和滚动淡入的内容出来,再冻结动画、回到顶部;
  - 每一次页面内的等待都有上限(字体加载可能永远不结束);
  - `background-attachment: fixed` 改成随页面滚动,否则长截图下半截是黑的;
  - 记录脚本语法错误、加载时未捕获的异常、页面卡死,交给第 5 节的运行门槛;
  - 渲染失败(我们没看到页面)和页面本身差要分开记:前者屏蔽,不算分。

## 3. 人工标注

- 同一份数据的两个页面并排、左右随机,不告诉来源;选「左好 / 右好 / 都好 / 都差」,并写一句理由。四选一沿用 DesignSense(arXiv 2602.23438)的做法,不逼人在差不多的两页里硬选。
- 混入同一提示词生成两次的页面对,看人自己在「差不多」时怎么判。
- 隔一段时间把一部分对左右对调重标,算人自己前后的一致率,作为 judge 一致率的上限。
- 页面对要覆盖不同水平:种子提示词、手写的几种提示词、更强的模型各生成一些。
- Pudding 这批默认原文比生成页好:「原文 vs 生成页」这一类对不做人工标注,当作「原文好」的已知答案(2026-10-20 定)。用在三处:检验 judge(两种顺序都判,应几乎总选原文,判错多就先改 judge);给 GEPA 当固定参照(候选页对原文的胜率或打平率);让模型逐对列出原文有、生成页没有的东西,作为归纳细则的候选,再由人确认。
  - 原文打开是开始按钮或视频的 6 篇(kidz-bop、boybands、stand-up、three-seconds、nba-unexpected、mow)不进这类对。
  - 原文都是英文,这批生成时固定写英文,免得 judge 按语言选。
  - 手绘插画、照片、署名和品牌元素是制作资源的差异,不是数据报告的能力:比较时让 judge 不看这些,归纳出的这类细则剔掉。
  - 「原文好」只指整体;按维度打分时不默认每一项都是原文好。

## 4. 从标注理由归纳 rubric

1. 把每条理由拆成一个个可检查的点。
2. 意思相同的点合并;每一类数出现在多少个不同的页面对里。
3. 只把出现次数够多的类写进 rubric;人从来没提过的不写。
4. 留出一部分标注不参与归纳,只用来验证 judge。

## 5. 校准 judge(照 MiMo 的做法)

### 5.1 judge 的结构

- **规则门槛,不交给 LLM**:脚本语法错误、加载时未捕获的异常、页面卡死记 0 分;正常加载的白页也记低分,不屏蔽。MiMo 实测截图 judge 看不出这类错误(有未捕获异常的页面 15% 仍被打了 0.5 分以上),而且门槛必须是 0 分,不能是打折:打折会被当成可以摊销的代价。
- **两个维度分开判**:一个 judge 只看数据有没有完整、正确地呈现(对应 MiMo 的 query judge),一个只看排版和信息组织(对应 MiMo 的 group pick)。各自的提示词里写明不评另一方面。
- **组内挑选,不打绝对分**:同一份数据的几个页面一起给 judge,只挑「明显更好」和「明显更差」的,允许回答「没有明显差别」。
- **去噪**:同一组判多轮,每轮按 Williams 拉丁方换顺序(每张图在每个位置各出现一次);票数太少的不算;多轮都判「没有明显差别」时整组不给分。MiMo 用这套把排在第一位的偏差从 ±0.28 票降到 ±0.03 票。

### 5.2 打磨流程(MiMo 4.2.2 节)

1. **一致性**:同一个 judge 对同一组重判几次,换另一家的模型再判;结论对不上的地方说明 rubric 有歧义,改写这一条。
2. **有效性**:收集不同水平生成的页面,对照人工标注和 judge 的理由,找两类错:太严(好页面被判差)、太松(差页面被判好)。每个错都查原因:是 rubric 写得不清楚、judge 看不出来,还是渲染出了问题。
3. **对抗页面**:手工做几种看起来对、其实不对的页面(板块堆满、到处塞图、内容藏进 tab、页面卡死),judge 必须识别出来。
4. **反复以上三步**,直到重判一致、找不到新的误判、对抗页面都被识别,rubric 才算定下来。

### 5.3 记录和冻结

- 每条打分记下 judge 模型、提示词的哈希和渲染器版本;改了任何一样,新旧分数不混在一起比。
- 评测用的 judge 单独一份、定下来后不再改,和优化时用的 judge 分开(MiMo 的评测细则就是逐字固定、用哈希锁住的)。
- 基础设施失败(渲染失败、judge 调用失败)单独计数,不当成 0 分混进平均分。

### 5.4 验收(数字待第 3 节标完再定)

- judge 和人工在留出标注上的一致率,接近人自己前后的一致率;
- 同一组换顺序重判,结论一致;
- 对抗页面全部识别。

## 6. GEPA 打分适配器

GEPA 要求每份数据上有一个能跨版本比较的分数,组内挑选给的是相对结果,所以:

- 每份验证和训练数据,先用种子提示词生成 2 个**参照页面**,只生成一次。
- 某个提示词版本在一份数据上生成 2 个页面,和这 2 个参照页面放成一组做组内挑选;它的分数由它的页面相对参照页面的得票算出,再按 5.1 的门槛和数据完整度扣分,映射到 0–1。PUPA(GEPA 论文的任务之一)的质量分也是每个回答和固定参照比。
- 反馈文字:judge 的理由、门槛没过的原因、数据完整度 judge 指出的缺漏。
- GEPA 设置先用论文的:小批量 3、帕累托挑选、子代在同样 3 份上总分严格变高才接受、返回验证集平均分最高的版本。

## 7. 最终评测

测试集上,最终提示词和种子提示词各生成页面,做人工盲评,同时用 5.3 的评测 judge 打分。两者对不上时以人工为准,先查 judge。
